# Authentication security assessment

Research date: 2026-09-22.

## Bottom line

Asking a user to paste either a Huly password or a bearer token into ordinary chat, an MCP tool argument, or another model-visible field is unsafe. Both values can be captured by transcripts, tool-call history, telemetry, support exports, screenshots, or logs. A password is worse because it is a reusable primary credential; a bearer token is still a secret that gives its holder the token's authority.

For the current product, prefer a Huly-managed API token over email/password when the target deployment supports the new token feature. Use a dedicated least-privileged Huly account, choose the shortest practical expiry, and inject the token through a client secret store or protected environment/configuration boundary. This improves rotation, expiry, workspace binding, and revocation, but it does **not** provide fine-grained permissions: Huly's new API tokens carry the account's full rights in their workspace.

Huly's existing OpenID Connect support does not solve API delegation. Huly is an OIDC relying party for interactive browser sign-in; the public Platform API client does not expose an OAuth authorization-code, device-code, or refresh-token flow for third-party clients. OAuth 2.1 is still the right design for authenticating clients to a hosted MCP endpoint, but that MCP access token must remain separate from the downstream Huly credential.

## Verified facts

### Public Huly Platform API authentication

The official Huly API client documents exactly two authentication shapes: email plus password, or a token. Either gives the client the same resource access as the authenticated user ([official API client README](https://github.com/hcengineering/huly.core/blob/981aaf40752109e78f8bb7ac20ee9aa33e110ea1/packages/api-client/README.md#L45-L85)). The current source type is likewise a union of `PasswordAuthOptions` and `TokenAuthOptions`; there is no OAuth/OIDC option in the public connection contract ([types](https://github.com/hcengineering/platform/blob/c864345e0fcc7453c17cda97e8160b6d4fa9b19b/foundations/core/packages/api-client/src/types.ts#L166-L198)).

The implementation either exchanges email/password for an account token or accepts the supplied token, then calls `selectWorkspace` to obtain the workspace connection information and workspace token ([implementation](https://github.com/hcengineering/platform/blob/c864345e0fcc7453c17cda97e8160b6d4fa9b19b/foundations/core/packages/api-client/src/utils.ts#L28-L54)). This is a direct credential/token bootstrap, not a standardized delegated OAuth grant.

### Managed personal API tokens now exist on `develop`

Huly merged revocable API-token management in [platform PR #10624](https://github.com/hcengineering/platform/pull/10624) on 2026-08-04. Current `develop` lets an ordinary `User` create a token for a workspace they can access, with a validity period from 1 through 365 days. The signed JWT is bound to the account and workspace and includes an API-token identifier and expiry; the account can list and revoke its tokens ([account operations](https://github.com/hcengineering/platform/blob/c864345e0fcc7453c17cda97e8160b6d4fa9b19b/server/account/src/operations.ts#L2679-L2840)). The account UI reveals the secret when it is created and offers 7, 30, 90, 180, and 365-day expiries ([creation UI](https://github.com/hcengineering/platform/blob/c864345e0fcc7453c17cda97e8160b6d4fa9b19b/plugins/setting-resources/src/components/ApiTokenCreatePopup.svelte#L35-L163)).

The important limitation is explicit in the merged implementation: API tokens carry the account's **full rights**. Proposed read/write/delete scopes were removed because they were not enforced consistently across transports and transaction nesting ([merge description](https://github.com/hcengineering/platform/commit/5a3d673e8443419eaa21a1a46eb163489d81342d)). An API-token-authenticated session also cannot create, list, or revoke API tokens, which prevents a stolen token from renewing itself or disabling the owner's recovery credentials ([guard](https://github.com/hcengineering/platform/blob/c864345e0fcc7453c17cda97e8160b6d4fa9b19b/server/account/src/operations.ts#L2683-L2692)).

The current token verifier checks signature, expiry, and revocation. Revocation verdicts are cached for 60 seconds and an unavailable account authority fails closed when there is no trusted cached verdict ([token verifier](https://github.com/hcengineering/platform/blob/c864345e0fcc7453c17cda97e8160b6d4fa9b19b/foundations/core/packages/token/src/token.ts#L142-L230)). This makes the new tokens materially safer to rotate than an untracked session token, but revocation is not necessarily instantaneous on every service surface.

Availability is deployment-dependent. At the research date, official `develop` is `c864345e…`, containing the feature, while official `main` is `33f14136…`, predating it; the latest published platform release remains `v0.7.426` from 2026-07-05 ([official releases](https://github.com/hcengineering/platform/releases)). Do not promise the API-token settings UI on Huly Cloud or a self-hosted installation without checking that deployment. The more detailed compatibility and certification status is recorded in [platform-pr-10624-api-token-support.md](platform-pr-10624-api-token-support.md).

### Huly OIDC is interactive sign-in, not delegated API OAuth

Huly self-host supports configuring `OPENID_CLIENT_ID`, `OPENID_CLIENT_SECRET`, and `OPENID_ISSUER` for [OpenID Connect sign-in](https://github.com/hcengineering/huly-selfhost#configure-openid-connect). The implementation discovers the issuer, registers an authorization-code browser callback, requests `openid profile email`, maps the resulting identity to a Huly account, and redirects the browser into Huly ([OIDC provider source](https://github.com/hcengineering/platform/blob/c864345e0fcc7453c17cda97e8160b6d4fa9b19b/pods/authProviders/src/openid.ts#L35-L118)).

This can remove password entry from the human Huly login experience, especially for self-hosted SSO. It does not make Huly an OAuth authorization server for arbitrary integrations, and the official Platform API client exposes no corresponding delegated OAuth flow. No public Huly contract was found for third-party authorization-code/device-code exchange, consented scopes, refresh tokens, or OAuth authorization-server metadata.

### Huly cookies are browser session transport, not an integration credential type

Huly's account client can ask the account service to set or delete a cookie after it already has an authorization token ([account client](https://github.com/hcengineering/platform/blob/c864345e0fcc7453c17cda97e8160b6d4fa9b19b/foundations/core/packages/account-client/src/client.ts#L1268-L1289)). The service turns the supplied token into an account token without a workspace and sets an HTTP-only cookie ([account service](https://github.com/hcengineering/platform/blob/c864345e0fcc7453c17cda97e8160b6d4fa9b19b/server/account-service/src/index.ts#L306-L335)). This supports browser session behavior; it is not a distinct least-privilege API key or a public API-client authentication mode.

### This repository's current credential boundary

Hulymcp accepts either `HULY_TOKEN` or `HULY_EMAIL` plus `HULY_PASSWORD`; the token takes precedence. Both password and token values become Effect `Redacted` values at the configuration boundary ([config](../../src/config/config.ts#L99), [environment loading](../../src/config/config.ts#L233)). Hosted request-scoped configuration deliberately accepts a token header only, not password headers ([header configuration](../../src/config/config.ts#L213)). The diagnostic surface reports only sanitized configuration state and does not return secret values ([README](../../README.md#built-in-diagnostic-tools)).

These controls reduce accidental exposure inside hulymcp, but they cannot make a secret safe after it has already been pasted into a chat or stored in a plaintext client configuration file. They also do not encrypt transport: both the remote MCP endpoint and Huly endpoint need HTTPS outside a trusted local boundary.

The Huly CLI has a different local flow from MCP client configuration. `huly auth login` reads the password through a hidden terminal prompt, exchanges it for a workspace token, and stores only that token ([login implementation](../../packages/huly-cli/src/local-commands.ts#L251)). The token is stored as cleartext JSON in the operating system's user configuration directory, separated from profile metadata; on POSIX systems the directory and files are restricted to modes `0700` and `0600` ([store implementation](../../packages/huly-cli/src/profile-store.ts#L79), [CLI documentation](../../packages/huly-cli/README.md#authentication-and-profiles)). This is safer than persisting the password and keeps it out of model-visible MCP traffic, but it is a permission-protected file, not an encrypted OS keychain. Malware or another process running as the same user can still read and reuse it.

The credential mechanisms should therefore be distinguished as follows:

| Mechanism | What is stored or transmitted | Security position |
| --- | --- | --- |
| MCP client JSON / environment configuration | Password or token commonly appears as a plaintext configuration value and is passed to the local server process environment | Acceptable only as a compatibility/configuration boundary with tight file ownership; never paste the value into chat. Prefer a token over a password. |
| Huly CLI profile login | Password is entered in a hidden prompt and discarded; resulting workspace token is stored in a mode-restricted cleartext JSON file | Better local UX and smaller persisted credential than storing the password, but not encrypted-at-rest keychain storage. |
| Huly managed API token | Workspace-bound bearer token with explicit expiry and revocation, but full account workspace rights | Preferred downstream Huly credential where supported; combine with a dedicated low-privilege account. |
| Huly browser OIDC | Human authenticates at an external IdP and Huly establishes its own browser login | Good for human SSO; not a published delegated API/MCP credential flow. |
| Standards-compliant MCP OAuth | Audience-bound OAuth token authorizes a client to the hosted MCP resource server | Preferred client-to-MCP boundary for hosted service; it is separate from, and must never be passed through as, the Huly credential. |

## Standards implications

OAuth's current security best practice says the resource-owner password credentials grant must not be used because it exposes the user's credentials to the client, expands the places from which they can leak, trains users to enter credentials outside the authorization server, and does not fit multi-step or two-factor authentication ([RFC 9700 section 2.4](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.4)). The same document says access-token privileges should be restricted to the minimum required, including audience, resources, and actions ([RFC 9700 section 2.3](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.3)). Huly's current full-rights API tokens do not meet the fine-grained part of that ideal, so account-level least privilege remains necessary.

For HTTP MCP, the 2026-07-28 specification defines the MCP server as an OAuth 2.1 resource server and the MCP client as an OAuth client. It requires discovery metadata, audience/resource binding, bearer tokens in the `Authorization` header rather than URI query strings, and validation that the token was issued specifically for the MCP server ([MCP authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). It explicitly forbids an MCP server from accepting or transiting unrelated tokens. Therefore an inbound MCP OAuth token must **not** be passed through to Huly; the two authorization legs need separate credentials and audiences.

The same MCP specification says stdio deployments should retrieve credentials from the environment rather than apply the HTTP OAuth flow. Newer MCP URL-mode elicitation exists specifically so sensitive credentials or third-party OAuth can be completed in a browser without exposing secrets to the MCP client ([official MCP release explanation](https://blog.modelcontextprotocol.io/posts/2025-11-25-first-mcp-anniversary/#url-mode-elicitation-secure-out-of-band-interactions)).

## MCP OAuth and browser onboarding in headless deployments

Provider-specific follow-up: [Optional bring-your-own MCP authorization](bring-your-own-mcp-authorization.md) verifies that an operator can reuse an existing suitable provider without imposing new identity infrastructure on local users. It also corrects the earlier draft-only characterization below: MCP now documents the [client-credentials extension](https://modelcontextprotocol.io/extensions/auth/oauth-client-credentials). It remains optional, and actual host/client interoperability requires verification; SDK support alone is insufficient.

MCP OAuth is normal for a **protected remote HTTP MCP server**, but it is not universally required. The normative MCP position is:

- Authorization is optional for an MCP implementation. If an HTTP transport supports authorization, it **SHOULD** implement the MCP authorization specification. Stdio implementations **SHOULD NOT** use that HTTP OAuth flow and should obtain credentials from their environment instead ([MCP protocol requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#protocol-requirements)).
- In a conforming protected HTTP deployment, the MCP server is the OAuth resource server and the MCP client is the OAuth client. The authorization server may be part of the same product, hosted alongside the MCP server, or be a separate identity provider; MCP does not prescribe who operates it. The MCP server advertises the appropriate authorization server through protected-resource metadata ([MCP roles](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#roles), [authorization-server discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)).
- The normal user-delegated profile uses the authorization-code flow. MCP clients **MUST** use PKCE, verify that the authorization server advertises PKCE support, and use `S256` when technically capable ([MCP authorization-code protection](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations#authorization-code-protection)). Client registration can be pre-arranged, use a Client ID Metadata Document, or use deprecated Dynamic Client Registration as a compatibility fallback ([MCP client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)).

The headless choice depends on whether a human is being represented:

| Deployment | Appropriate mechanism | Important limitation |
| --- | --- | --- |
| Local stdio launched by a user | Inject the Huly token through the process environment or a local secret/keychain adapter | This is intentionally outside MCP's HTTP OAuth flow. The launcher remains responsible for protecting the secret. |
| Remote client acting for a human | Complete authorization code plus PKCE once in a browser, then securely retain the resulting token material | A headless client still needs its redirect callback to be reachable; merely printing the authorization URL does not solve a callback bound to another machine ([RFC 8252 authorization flow](https://www.rfc-editor.org/rfc/rfc8252.html#section-4)). Refresh tokens are optional and the client cannot assume one will be issued ([MCP refresh-token guidance](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#refresh-tokens)). |
| Unattended CI/service identity | Use a pre-registered confidential OAuth client and the client-credentials grant if the chosen authorization server and MCP service support it | Client credentials represent the automation itself, not a human user. OAuth limits this grant to confidential clients and pre-arranged resources ([RFC 6749 section 4.4](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.4)). MCP's machine-to-machine client-credentials profile is currently a **draft, optional extension**, not guaranteed core interoperability ([official MCP authorization extensions](https://github.com/modelcontextprotocol/ext-auth), [draft client-credentials extension](https://github.com/modelcontextprotocol/ext-auth/blob/main/specification/draft/oauth-client-credentials.mdx)). |
| Headless terminal with a human available on another device | An authorization server may offer the OAuth device authorization grant | Device authorization is an optional OAuth extension, not a required MCP core capability, so client/server interoperability must be verified. It still requires a person to visit a verification URL and approve the request on another device ([RFC 8628](https://www.rfc-editor.org/rfc/rfc8628.html#section-1)). |
| Existing single-purpose deployment | A securely pre-provisioned audience-bound access token can be injected by the deployment secret manager | This can be operationally useful, but a static shared bearer-token scheme without MCP discovery, registration, and authorization-server behavior is not a full implementation of the MCP OAuth specification. |

Browser onboarding is a separate leg. URL-mode elicitation is designed for the MCP server to request downstream credentials or third-party authorization without exposing them to the MCP client; it **must not** be used to authorize the MCP client's access to that MCP server ([MCP URL-mode distinction](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation#url-mode-elicitation-requests)). Support is capability-negotiated and therefore cannot be assumed: a server must not send URL-mode elicitation to a client that did not advertise it. Even when supported, the client's `accept` response records consent to visit the URL, not proof that the external operation completed; the server must check its own bound state when the request is retried ([MCP URL-mode flow](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation#example-request-sensitive-data)).

For Huly specifically, interactive onboarding can direct a user to a hulymcp-owned HTTPS page that stores a managed Huly token in a keychain or encrypted server-side vault. It cannot silently mint that Huly token because Huly does not currently expose a delegated OAuth grant. In a truly unattended environment, onboarding does not run: an operator provisions the Huly token before startup through the CI/orchestrator secret store. A headless terminal with a human available may print or otherwise present an out-of-band setup URL through a separate CLI/control-plane flow, but that fallback is product behavior, not something URL-mode-capability support can be assumed to provide.

## Recommendations

These are design recommendations derived from the verified facts above, not claims about currently implemented behavior.

1. **Never collect Huly passwords or tokens through model-visible inputs.** Do not add a `login`, `set_token`, or similar MCP tool that accepts a secret. Keep credentials out of prompts, tool arguments, URLs, command-line arguments, generated files, errors, and diagnostic output.
2. **Make managed Huly API tokens the preferred upstream credential when available.** Detect or document the deployment prerequisite, use the shortest practical expiry, rotate regularly, and provide revocation guidance. Continue to call them full-rights bearer credentials, not scoped tokens.
3. **Use a dedicated Huly integration account.** Give it only the workspace role and space membership needed by the automation. This is currently the effective least-privilege control because Huly API-token scopes do not exist.
4. **Treat password auth as a compatibility fallback.** If it must remain, acquire and store the password outside model-visible flows, preferably through an OS keychain, container/orchestrator secret, or equivalent secret injection. Never place a real value in checked-in JSON, shell history, examples, or support artifacts.
5. **Implement standards-based OAuth for a hosted MCP endpoint.** Use a dedicated authorization server/IdP; publish protected-resource and authorization-server metadata; use authorization code with PKCE, audience binding, short-lived access tokens, and meaningful MCP scopes. Replace the current static `MCP_AUTH_TOKEN` mode for multi-user hosted deployments rather than confusing it with Huly authentication.
6. **Keep the two auth legs separate.** Map the authenticated MCP principal to a server-side encrypted Huly credential. Never use an inbound MCP bearer as `HULY_TOKEN`, and never expose the stored Huly credential back to the MCP client or model.
7. **Prefer an out-of-band browser connection flow.** When client support permits, use MCP URL-mode elicitation to open a hulymcp-owned connection page. The page can accept/store a Huly API token directly or, on a compatible Huly deployment, guide the user through Huly sign-in and API-token creation. The MCP client should receive only success/failure and a nonsecret connection identifier.
8. **Require HTTPS and secret-safe infrastructure for remote use.** Terminate TLS correctly for both client-to-MCP and MCP-to-Huly traffic, reject secrets in query strings, redact credential headers at proxies/APM, avoid request-body capture, encrypt stored downstream credentials, and restrict filesystem/config permissions.

## Suggested product sequence

1. Update setup guidance so token auth is recommended first and password auth is explicitly labeled fallback; add a warning never to paste either secret into chat.
2. Add deployment/version guidance for Huly's new revocable API tokens and finish the existing compatibility certification before making a broad support claim.
3. Move the CLI token file behind an OS keychain/credential-store adapter where available, retaining the restricted-file store only as an explicit fallback. Write no secret to stdout or model-visible responses.
4. For hosted multi-user service, implement MCP OAuth 2.1 at the HTTP boundary and store per-principal downstream Huly credentials separately.
5. Add URL-mode browser onboarding when target MCP clients support it.
6. Revisit true delegated Huly OAuth only if Huly publishes an authorization-server/API contract. Do not build against the current internal OIDC callback/token exchange as if it were a stable third-party API.
