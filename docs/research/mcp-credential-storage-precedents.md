# MCP credential storage precedents

Researched 2026-09-22 for the authentication implementation tickets. This is a bounded primary-source survey, not a ranking or security audit. Publisher-maintained projects were preferred; preview products and smaller implementations are identified separately. No external implementation was executed.

## Finding

Keep optional OS storage for shared CLI/stdio profiles. There is direct server-side precedent, including Microsoft's PostgreSQL MCP server, rather than only client-side OAuth caches. This supports the shape of the accepted design; it does not establish that all MCP servers should own a keychain or justify changing the existing file-storage default. Preserve environment injection for headless/container use. Native storage must earn its recommendation through real noninteractive and failure testing.

The first search surfaced mainly MCP clients, gateways and environment-based server configuration. A second, differently phrased search explicitly targeted server-side `keyring`, `credentials`, and shared CLI implementations. It found the direct precedents below. Therefore the user-requested repeat search was performed, and there is no evidential basis for “nobody does it.” This is not an exhaustive adoption measurement.

## Concrete examples and responsibility boundaries

| Project | Whose credential storage? | Observed contract and limitation |
| --- | --- | --- |
| Microsoft postgres-mcp | Server and its connection-management CLI | Named profiles have nonsecret YAML; a hidden CLI prompt stores passwords in macOS Keychain, Linux Secret Service or Windows Credential Manager. Stdio retrieves credentials when connecting. A connection-string environment path supports hosts without a keyring. MCP profile creation does not accept passwords. Publisher-owned **Preview**, not a mature security benchmark; reviewed documentation, not binary behavior. [Usage](https://github.com/microsoft/postgres-mcp/blob/4e69353c5626b2418e05e199c1eead6b2b7def44/USAGE.md), [status](https://github.com/microsoft/postgres-mcp/blob/4e69353c5626b2418e05e199c1eead6b2b7def44/README.md). |
| GitHub MCP server | Local server's upstream GitHub credentials | Stdio supports environment PATs, which take precedence, and browser OAuth with memory-only tokens. This is evidence that persistence is a product choice, not required by MCP. The documented URL-elicitation path keeps authorization URLs outside model context; tool-response fallback is weaker. [Local OAuth](https://github.com/github/github-mcp-server/blob/85598ba6e1256f7ebf4867b95d63b833c4549264/docs/oauth-login.md). |
| Sentry MCP server | Hosted server's upstream Sentry credentials, distinct from client-facing MCP tokens | The OAuth deployment holds upstream credentials in encrypted grant properties, uses them for Sentry calls, and gives clients a separate MCP token. Rejected upstream credentials require renewed authorization. A separately selected direct-token mode also exists. This supports explicit trust-boundary separation, not copying Sentry's scopes, storage implementation or refresh behavior. [Security model](https://github.com/getsentry/sentry-mcp/blob/1bd2754322df766acfb95692a937774957a61dc2/docs/operations/security.md). |
| AWS MCP proxy | Server/proxy uses the existing AWS credential ecosystem | Resolves credentials through the boto3 chain, including environment and shared credentials files, with profile configuration. Reusing an established provider credential chain is an alternative to building another secret store; Huly does not thereby acquire such a chain. [AWS-owned implementation](https://github.com/aws/mcp-proxy-for-aws). |
| jcodemunch-mcp | Server-side optional keyring resolver plus management CLI | Source implements `keyring:<name>` references and shared keyring operations. This is a smaller independent implementation, useful as a second concrete precedent, not a quality endorsement. Its environment mutation, exception handling and soft-failure behavior should not be copied into this project's typed boundaries. [Pinned source](https://github.com/jgravelle/jcodemunch-mcp/blob/fbff5f823c647eeff391193283cf40f14a8c45bb/src/jcodemunch_mcp/credentials.py). |
| Docker Sandboxes MCP gateway | Host/gateway credentials used to access MCP servers | MCP OAuth client secrets and header secrets use the host store and remain outside sandboxes. Desktop stores include Keychain and Secret Service. Headless Linux can fall back to files with a notice. This is **gateway/client-side** evidence; its fallback policy differs from our accepted explicit-backend policy. [Docker documentation](https://docs.docker.com/ai/sandboxes/configuration/credentials/#mcp-secrets). |

The [MCP 2025-06-18 authorization specification](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization) distinguishes HTTP authorization from stdio environment credentials. It also requires resource-bound token validation and authorization on each HTTP request. A saved local profile is an application convenience; it must not turn stdio into an HTTP OAuth admission protocol or cause an incoming MCP token to become an upstream Huly token.

## Native storage lessons

**No prompts is an adapter capability to prove.** Linux Secret Service can return a prompt object when an operation needs interaction; the client must invoke its `Prompt()` method to display it. Reject that condition with an actionable typed error during normal CLI/stdio work. Test the selected binding, since convenience libraries may automatically unlock or prompt. The API also distinguishes the user's session, collections and items. Document that a CLI and IDE-launched stdio process need access to the same intended user/session service; a container is not automatically attached to the host's keyring. [Secret Service specification](https://specifications.freedesktop.org/secret-service/latest-single/).

On macOS, authentication UI may be allowed by default by the relevant API. Apple's keychain implementations differ, so a cross-platform wrapper's advertised Keychain support does not establish that it can satisfy the no-prompt contract. Select an adapter that can enforce noninteractive access and verify the actual packaged executable's behavior for locked, unavailable and denied access. Do not prescribe one API flag without checking its applicability to that backend. [Authentication UI control](https://developer.apple.com/documentation/security/ksecuseauthenticationui), [macOS implementation differences](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains).

**Test storage reality, not only the reported backend.** A Google Workspace CLI issue reports an encryption key being co-written to disk despite keyring status. This is a reporter's observation on an identified version, not an independently reproduced claim about current releases. It motivates checking that native-backed saves, reads, status and failures do not create plaintext token copies or encryption-key sidecars in application-managed files. Google's current project should be treated as an adjacent CLI example here, not asserted to be a current MCP server. [Reported regression](https://github.com/googleworkspace/cli/issues/791), [credential-store source](https://github.com/googleworkspace/cli/blob/main/crates/google-workspace-cli/src/credential_store.rs).

OS storage protects stored credentials; it is not a guarantee against arbitrary code running with the user's privileges. Keep secrets out of model-visible tools, errors and diagnostics even when storage is native. Do not expose a secret-reading MCP tool as the way to use saved credentials. The Microsoft design above demonstrates an out-of-band secret-management path.

## Additive ticket guidance

These are implementation checks within accepted scope, not new product decisions.

- **Use saved profiles from CLI and stdio / Import and manage local tokens safely:** document who owns each credential and support externally injected credentials without copying them into persistence. Keep human secret input outside MCP tool arguments and results. Cite Microsoft's CLI/profile design and the MCP transport distinction.
- **Use macOS credential storage / Use Linux credential storage:** test the actual packaged CLI and client-launched stdio under the intended user/session; assert prompt-free ordinary operations, no app-managed plaintext/sidecar duplicates, accurate backend reporting, and typed denied/locked/unavailable failures. Explain headless/container prerequisites and the existing explicit environment/file alternatives. Do not silently adopt another project's fallback.
- **Authenticate and discover hosted MCP / Run identity-isolated hosted Huly operations / Provision durable machine connections offline / Connect a human account through the browser:** test both directions of the credential boundary: MCP tokens never authenticate upstream Huly requests, and upstream Huly secrets never appear in MCP outputs, setup responses, status or diagnostics. Sentry supplies a concrete separate-token architecture reference; the MCP specification supplies audience requirements.
- **Complete MCP-triggered setup and retry:** distinguish URL elicitation from model-visible fallback. Legacy tool text must contain only a safe setup link, never credentials or a bearer capability. Browser authentication and identity binding remain necessary; receiving a URL is not authorization. GitHub's fallback discussion is supporting precedent.

No evidence requires reopening the accepted destination, imposing mandatory native storage, changing defaults, adding migration or introducing new authorization scopes. Native implementation qualification remains outstanding work for those implementation tickets.
