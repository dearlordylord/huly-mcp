# Intabia source compatibility assessment

Checked 2026-09-13. This is a bounded source audit, not a live compatibility certification. The checked commit is the current repository checkout; released self-host images and cloud deployments may run different commits. Apply findings only after matching their source tag/image digest and observed config, not merely the Intabia product name.

Intabia was shallow-cloned into ignored `.reference/intabia-platform`, at [`be9f942e4ea285e38a4faad49a02211d95b76bdb`](https://github.com/intabia-fusion/platform/tree/be9f942e4ea285e38a4faad49a02211d95b76bdb). The checkout is clean. Our comparison baseline is [`3fe939344caac5e71b6942df438aa961c856c11e`](https://github.com/dearlordylord/huly-mcp/tree/3fe939344caac5e71b6942df438aa961c856c11e), using the installed packages pinned in package.json: api-client 0.7.19 (patched), account-client 0.7.25, collaborator-client 0.7.18, core 0.7.26 and plugin packages 0.7.0. No dependencies were installed and no live workspace was modified.

## Finding: a concrete connection blocker

Intabia moved collaborator discovery from global frontend configuration into the selected workspace response:

- Its [ServerConfig](https://github.com/intabia-fusion/platform/blob/be9f942e4ea285e38a4faad49a02211d95b76bdb/foundations/core/packages/api-client/src/config.ts) has ACCOUNTS_URL, FILES_URL and UPLOAD_URL, without COLLABORATOR_URL. Its [frontend config assembly](https://github.com/intabia-fusion/platform/blob/be9f942e4ea285e38a4faad49a02211d95b76bdb/server/front/src/index.ts#L335) likewise omits COLLABORATOR_URL, although extraConfig can inject fields.
- Its [WorkspaceLoginInfo](https://github.com/intabia-fusion/platform/blob/be9f942e4ea285e38a4faad49a02211d95b76bdb/foundations/core/packages/account-client/src/types.ts#L56) has optional collaboratorEndpoint. Its [connectRest](https://github.com/intabia-fusion/platform/blob/be9f942e4ea285e38a4faad49a02211d95b76bdb/foundations/core/packages/api-client/src/rest/rest.ts#L70) passes info.collaboratorEndpoint to the REST client.
- Our [connectRest](../../src/huly/client.ts#L710) instead passes serverConfig.COLLABORATOR_URL to createMarkupOps; createMarkupOps constructs the collaborator client immediately. The installed collaborator-client getClient immediately calls replaceAll on that argument. Therefore, inference from source: default Intabia configuration will cause connection initialization to throw on undefined, even for a read-only list tool. This has not been reproduced against a running deployment. A custom frontend config could mask it.

A likely adaptation is schema-owned discovery of the workspace-specific collaborator endpoint with a fallback to the existing global endpoint; that is a proposed change, not implemented here. Verify the actual deployment response before choosing precedence and normalize ws/wss as the SDK does.

## Other material risks

Intabia's [REST client](https://github.com/intabia-fusion/platform/blob/be9f942e4ea285e38a4faad49a02211d95b76bdb/foundations/core/packages/api-client/src/rest/rest.ts#L80) explicitly decodes policy errors and makes HTTP 403 non-retryable for tx. Its accompanying [retry utility](https://github.com/intabia-fusion/platform/blob/be9f942e4ea285e38a4faad49a02211d95b76bdb/foundations/core/packages/api-client/src/rest/utils.ts) adds shouldAbort; our installed api-client source lacks this addition. Probe deterministic quota/permission failures for useful error mapping and accidental retries before declaring write support.

[Contact migrations](https://github.com/intabia-fusion/platform/blob/be9f942e4ea285e38a4faad49a02211d95b76bdb/models/contact/src/migration.ts#L565) include social-identity creation, account UUID fill, user-profile migrations and social-identity deletion flags. A matching latest interface is insufficient evidence for an older or incompletely migrated workspace. Record model version and migration completion with test results.

Our rich-text URLs are constructed as /browse?workspace=... and /files?workspace=...&file=... in [createMarkupOps](../../src/huly/client.ts#L675). Validate links and images through the actual Intabia UI, not just equality of returned Markdown. Deployment-specific frontend routing is not certified by this audit.

## Concrete validation sequence

1. Pin fork commit, deployment image digest/version, our package version, SDK versions, frontend config and model version. Keep credentials and tokens out of artifacts.
2. Compare only our actual I/O surface first: sdk-deps.ts, client.ts, storage.ts, workspace-client.ts, SDK serializers and consumed plugin classes/attributes. Produce per-capability statuses: present, differs, absent, untested. Package-wide text diffs are useful evidence but are not a pass/fail oracle.
3. Read-only live preflight: config.json; login/token workspace selection; collaborator endpoint resolution; account; full model; one bounded find-all in each advertised module. Evaluate hierarchy/class/attribute existence against the actual loaded model. Confirm old core can build the model before fixture writes.
4. On a disposable test workspace, run focused vertical slices: issue with assignee/status/labels/subtask; rich document Markdown/HTML with image and internal link; chat/thread; attachment upload/download byte comparison; update/delete and eventual-consistency polling. Assert resulting UI-visible state and cleanup.
5. Then run the existing full integration suites with a capability report, including owner/member/guest and cross-workspace negative tests. Quota/policy rejection, archived entities, pagination, Unicode, empty/null optional fields and migrated social identities are additional high-value cases.
6. Certify capability sets against the exact deployment version. An Intabia SDK control client is useful for distinguishing server limitations from failures in our older Huly adapter; run that comparison in an isolated dependency environment. Neither a successful login nor a successful issue CRUD test establishes support for every MCP tool.

No live test or full quality gate was run as part of this source-only research subtask.
