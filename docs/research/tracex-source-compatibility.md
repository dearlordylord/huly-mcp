# TraceX source compatibility with huly-mcp

Checked 2026-09-13. This is a bounded source comparison, **not a claim of tested deployment support**.

TraceX was shallow-cloned into ignored `.reference/tracex`, branch `develop`, commit `a5dcad32bf888b85b3261151114850669c7a23ed`. No dependencies were installed and no live workspace was accessed. Our baseline is commit `3fe939344caac5e71b6942df438aa961c856c11e` plus the installed, lockfile-pinned Huly SDK sources/source maps. A deployed TraceX release must be identified independently: its README distinguishes stable `v*` releases from development `s*` builds. A moving `develop` checkout cannot certify either a stable image or their cloud. [Release convention](https://github.com/TraceX-dev/TraceX/blob/a5dcad32bf888b85b3261151114850669c7a23ed/README.md)

## Result

Basic connectivity looks promising: the fork preserves the account/config/REST/collaborator contracts we actually use. Full tool compatibility is unproven, with concrete differences in authentication, card models and rich text. Matching package names and version numbers is insufficient.

## Concrete differences to exercise

1. **2FA password login is not supported by our existing flow.** TraceX returns `tfaRequired` and an intermediate token with `NIL_UUID` for accounts with 2FA; completion requires `verify2fa`. Our SDK `getWorkspaceToken` immediately selects the workspace and never completes that challenge. Prefer a TraceX-generated workspace API key as the initial automation credential candidate: keys are JWTs containing an `apiKey` identifier and have server-side revocation checks; workspace selection verifies that the key belongs to the requested workspace. This is source evidence for a viable token path, not a successful connection test. Test valid, wrong-workspace and revoked keys. [Login and API-key creation](https://github.com/TraceX-dev/TraceX/blob/a5dcad32bf888b85b3261151114850669c7a23ed/server/account/src/operations.ts), [Workspace selection API-key checks](https://github.com/TraceX-dev/TraceX/blob/a5dcad32bf888b85b3261151114850669c7a23ed/server/account/src/utils.ts)

2. **Cards diverge structurally and semantically.** TraceX's `Card` extends `VersionableDoc`; `CardSpace` extends `TypedSpace`; `Role` extends the core role attached to a space type and adds `types`, instead of the installed card role attached to a master tag. Version state includes optional `baseId`, `version`, `isLatest`, `isEffective`, `readonly`; cards additionally have `readonlySections` and `readonlyFields`. Shared class IDs and basic title/content fields remain, but successful creation of a simple card says little about versioned, effective or protected cards. Exercise dynamic type lookup, typed space membership and permissions, version selection, and rejected writes to protected content. [Card interfaces](https://github.com/TraceX-dev/TraceX/blob/a5dcad32bf888b85b3261151114850669c7a23ed/plugins/card/src/index.ts), [Version fields](https://github.com/TraceX-dev/TraceX/blob/a5dcad32bf888b85b3261151114850669c7a23ed/foundations/core/packages/core/src/versioning.ts)

3. **Tracker fields have changed.** TraceX makes `Project.defaultIssueStatus` optional and adds non-optional nullable `startDate` to Issue and Milestone, plus typed Gantt `IssueRelation` data. Our issue create path does not populate this new field. Server acceptance/defaulting and resulting UI behavior need a live fixture test; the interface difference alone does not establish a failing write. Existing tracker plugin ID remains `tracker`, with existing Issue/Project entries retained. [Tracker interfaces and IDs](https://github.com/TraceX-dev/TraceX/blob/a5dcad32bf888b85b3261151114850669c7a23ed/plugins/tracker/src/index.ts)

4. **TraceX-authored rich text is a necessary test class.** The fork's markdown serializer adds `file`, `drawingBoard`, subscript/superscript/highlight and review-related marks. Our installed serializer throws for unknown nodes/marks. This creates a specific read/conversion failure risk for native TraceX content even if our own plain markdown round trips pass. The fork also changes file-id image URL construction; verify rendered images, file links and browse URLs in the UI. Include TraceX-created fixtures and define which structures must survive editing before enabling writes on them. [TraceX markdown serializer](https://github.com/TraceX-dev/TraceX/blob/a5dcad32bf888b85b3261151114850669c7a23ed/foundations/core/packages/text-markdown/src/serializer.ts); compare installed `node_modules/@hcengineering/text-markdown/src/serializer.ts` and our [markup operations](../../src/huly/operations/markup.ts).

5. **Plugin presence must be checked in the actual workspace model.** TraceX source includes tracker, ordinary documents, controlled documents, card, recruitment, leads, inventory and test-management model builders. This is evidence against assuming the fork removed all Huly applications, but it does not prove every deployed workspace enables or initializes them. Produce a class/attribute/status capability inventory from `load-model`; distinguish missing classes, missing fixture data, permissions, and actual protocol errors. [Model catalog](https://github.com/TraceX-dev/TraceX/blob/a5dcad32bf888b85b3261151114850669c7a23ed/models/all/src/index.ts)

## Minimum diagnostic reproductions

- **Bootstrap:** point the unchanged built MCP at the chosen TraceX origin/workspace with a generated workspace key; call one existing read tool and capture only redacted error metadata. Repeat with password auth on a 2FA account to demonstrate the unsupported challenge separately from endpoint reachability.
- **Markup:** create a document/card in the TraceX UI containing an inline file and highlighted text, then retrieve it using our existing markdown-returning tool. Compare with a plain paragraph fixture. A serializer failure here isolates content compatibility from successful collaborator transport.
- **Tracker:** create one issue using our normal tool without a start date, reconnect, and inspect both persisted `startDate` and the TraceX Gantt/UI behavior. This decides whether the new interface field actually requires an adapter.
- **Cards:** read and attempt an authorized update on a disposable versioned card plus a protected version. Verify which version changed and whether server permissions reject the protected write; do not treat a success response alone as semantic correctness.

These are proposed tests, not executed results.

## Recommended order

1. Pin an actual TraceX image/release and record its source correspondence, configuration and workspace model identity.
2. Run read-only startup with a disposable workspace API key, then account/model/one-query/collaborator/storage preflight. Distinguish transport failure from an absent application.
3. Run existing Huly CRUD integration scenarios against enabled shared applications in an isolated fixture workspace, using the unchanged MCP and SDK as the first baseline.
4. Add TraceX-specific fixtures: 2FA/token/revocation, typed/versioned cards, permissions, Gantt fields, rich text with native nodes/marks, and link rendering. Check results through a fresh client and the TraceX UI/native API, not only through our own serializer.
5. Publish support by tested release and tool family. Native TraceX MCP availability demonstrates their own integration strategy; it does not prove our independent server is compatible or covers their extensions.

No full test suite was run for this research-only note. No binary compatibility, deployed version provenance or live authorization behavior has been established.
