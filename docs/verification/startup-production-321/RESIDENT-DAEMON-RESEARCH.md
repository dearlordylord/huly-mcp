# Resident MCP daemon research

Research snapshot: 2026-10-17. Five Luna agents at maximum reasoning covered lifecycle, bridges, security, the local source contract, and an independent adversarial source check. This note examines primary-source repository code, documentation, and issue history for shared local MCP processes. It does not install or run the compared projects. Source pins are recorded below so the implementation claims can be revisited.

## Strongest lifecycle analogue: MCPorter

[MCPorter v0.14.3](https://github.com/openclaw/mcporter/tree/1e3fa8a893e3245a0843f714f81bfdf3b0ad5dbc) has a single daemon per OS user in its canonical default namespace, reached through a fixed Unix-domain socket or Windows named pipe; configuration paths, working directories, and HOME/XDG overrides do not silently create additional production daemons. An explicit `MCPORTER_DAEMON_DIR` can select another namespace. This avoids dynamic TCP-port discovery, but means daemon ownership and isolation must be explicit. Clients resolve their own definitions and register immutable views. Calls carry a daemon generation, opaque view handle, and local server alias; tool visibility is checked again by the host. Shared transports remain alive when a CLI client exits, while abandoned views expire. [Pinned daemon design](https://github.com/openclaw/mcporter/blob/1e3fa8a893e3245a0843f714f81bfdf3b0ad5dbc/docs/daemon.md)

Startup has two coordination layers. The client first verifies daemon status and can launch a detached host, then waits for authenticated readiness. Separately, the host takes a cross-process bind lock before claiming the socket; a competing host exits after observing the already-live owner. Metadata is written atomically. The lock helper uses an exclusive lock file and checks recorded PID liveness when deciding whether a lock is stale. This prevents ordinary simultaneous starts, but PID-only lock liveness can mistake a reused PID for a still-held lock and delay recovery (inference from the pinned [lock/metadata code](https://github.com/openclaw/mcporter/blob/1e3fa8a893e3245a0843f714f81bfdf3b0ad5dbc/src/fs-json.ts)). Destructive retirement is stricter: migration records process start identities to distinguish PID reuse and does not signal a PID based only on stale metadata.

The documented recovery policy favors avoiding duplicate owners over automatic availability. Broker transport process-tree records are held in memory; host metadata does not preserve that full inventory across a host crash. Blocking replacement is not proof that orphan children have exited. [Broker ownership](https://github.com/openclaw/mcporter/blob/1e3fa8a893e3245a0843f714f81bfdf3b0ad5dbc/src/daemon/broker.ts), [host metadata](https://github.com/openclaw/mcporter/blob/1e3fa8a893e3245a0843f714f81bfdf3b0ad5dbc/src/daemon/host.ts), [replacement refusal](https://github.com/openclaw/mcporter/blob/1e3fa8a893e3245a0843f714f81bfdf3b0ad5dbc/src/daemon/client.ts). An unexpected daemon exit leaves metadata that blocks replacement until an operator verifies owned transports are retired. A live or unverified legacy daemon also blocks startup. The migration path requires upgrading all clients, draining old work, inspecting legacy owners, and explicitly confirming the drain; a mixed old/new client fleet cannot claim exclusive ownership. Protocol-generation mismatches fail closed. This makes upgrades a coordinated cutover, not “new client kills whatever owns the port.” [Migration and retirement behavior](https://github.com/openclaw/mcporter/blob/1e3fa8a893e3245a0843f714f81bfdf3b0ad5dbc/src/daemon/migration.ts)

Shutdown distinguishes transport idleness from host idleness. Per-server idle expiry occurs only after queued and active calls finish; a host-level idle timeout is controlled by canonical user configuration and waits for active calls, browser ownership, unknown-outcome calls, or failed retirements to clear. A timed-out operation is never replayed because its outcome is unknown. Retirement failure blocks replacement rather than allowing overlapping child processes. The docs make clear that a retained MCP session also retains shared state: views and tool filters do not isolate stateful server behavior. [Pinned lifecycle rules](https://github.com/openclaw/mcporter/blob/1e3fa8a893e3245a0843f714f81bfdf3b0ad5dbc/docs/daemon.md)

Windows is an implemented path: user/namespace-specific named pipes, current-user directory ACL verification and connection-bound mutual HMAC challenges. However, cleanup guarantees differ by path. Strict migration retirement checks process ownership/start identity; ordinary stdio close uses a separate helper that discovers Windows descendants by numeric PID and signals them without the same creation/owner revalidation. Do not generalize the stricter path to every shutdown. The cited process-level concurrent-start test skips Windows, despite passing Windows CI; our survey runs no native Windows validation. [Locator/access checks](https://github.com/openclaw/mcporter/blob/1e3fa8a893e3245a0843f714f81bfdf3b0ad5dbc/src/daemon/paths.ts), [strict migration retirement](https://github.com/openclaw/mcporter/blob/1e3fa8a893e3245a0843f714f81bfdf3b0ad5dbc/src/daemon/process-retirement.ts), [ordinary transport cleanup](https://github.com/openclaw/mcporter/blob/1e3fa8a893e3245a0843f714f81bfdf3b0ad5dbc/src/runtime-process-utils.ts), [race-test evidence](https://github.com/openclaw/mcporter/pull/195).

Historical issues are useful evidence of failure modes, not evidence that the current pinned release still has them. [Issue #191](https://github.com/openclaw/mcporter/issues/191) reported orphan processes, lost PIDs, socket-only liveness, and a parallel-start race in an earlier release. The merged [PR #195](https://github.com/openclaw/mcporter/pull/195) added host-side bind coordination because direct foreground/service starts could bypass the client lock; its author reports repeated concurrent-start trials leaving one survivor. That is maintainer-reported test evidence, not an independent reproduction here. [Issue #188](https://github.com/openclaw/mcporter/issues/188) separately reported a keep-alive bug in v0.7.3 that spawned 289 child processes and accumulated 12.81 GiB in 48 hours. A later May29 maintainer comment reports fix56be50f, a live regression and passing tests/CI, superseding the earlier bot assessment that the path was unproven. This is attributed evidence, not our independent runtime verification; its lesson is that daemon singleton correctness does not prove child-transport reuse or reaping is correct.

MCPorter is a useful pattern for ownership, view scoping, authenticated readiness, drain, and deliberate upgrade. It is not a loopback-HTTP implementation: it uses OS IPC and is a TypeScript package that runs under its supported JS runtime. Its production-wide per-user singleton also makes the host responsible for validating every client’s resolved transport identity and caller-specific exposure policy.

## Other shapes

[punt-labs/mcp-proxy](https://github.com/punt-labs/mcp-proxy/tree/31c59f2edecbeedcd129e2eb2f203839e2f83e10) is a compiled Go stdio-to-shared-daemon bridge using WebSocket. Its README says the proxy connects to a daemon that is already running; it supplies health/reconnect behavior, not a serialized auto-start/singleton supervisor. The documented platform support is macOS and Linux, with no Windows path. This is evidence that a small standalone connector can avoid requiring a Node runtime, but it does not solve daemon discovery, concurrent first-start, or upgrade ownership. [Pinned README](https://github.com/punt-labs/mcp-proxy/blob/31c59f2edecbeedcd129e2eb2f203839e2f83e10/README.md)

[mcp-control-plane](https://github.com/moorej2400/mcp-control-plane/tree/addc8b517c54ef2a516c888d86f296837f0cf022) describes a closer stdio-to-local-Streamable-HTTP shape: `mcpctl connect` starts or attaches to a shared service and bridges stdio. Its architecture discusses shared pools for compatible stateful servers and a pool-size limit for servers that assume one client per process. However, the repository at this pin is an early six-commit project with no release history and requires Node 22/npm. Treat its lifecycle and compatibility statements as design documentation, not field-validated behavior. [Pinned architecture](https://github.com/moorej2400/mcp-control-plane/blob/addc8b517c54ef2a516c888d86f296837f0cf022/docs/architecture.md) [pinned README](https://github.com/moorej2400/mcp-control-plane/blob/addc8b517c54ef2a516c888d86f296837f0cf022/README.md)

## Implications for a stdio-to-loopback-HTTP bridge

The useful recurring pattern is to make a stable owner discoverable, but require an authenticated readiness/status exchange before the client trusts it. Protect the start/bind operation across *all* entrypoints, not just clients that use the ordinary connector. Store atomic, versioned owner metadata, but treat a PID as a hint: verify endpoint identity before use and use process-start identity or an equivalent ownership proof before signaling or deleting state. Decide explicitly whether an unverified crash blocks startup for operator recovery or permits a bounded, provably safe cleanup; automatic “stale PID, kill it” risks targeting a reused PID.

A fixed loopback port is simpler than port scanning but creates a cross-version and cross-install collision domain. If using an allocated port, publish it only after bind under the singleton lock and authenticate the endpoint before sending credentials or configuration. Keep protocol version, daemon generation, compatible backend identity, and caller-scoped exposure policy separate and explicit. Drain active calls before shutdown or replacement; never replay mutations whose outcome is unknown. Test idle shutdown, a killed daemon, stale metadata, simultaneous connectors from separate parents, two package versions racing, and Windows process-tree cleanup as lifecycle cases.

The project’s reported 0.57 GiB HTTP measurement is daemon-only: its ten SDK clients lived inside one benchmark parent. It does not include ten new stdio adapter processes, so it cannot support a total-resident-memory claim or characterize adapter RSS. See the [matched transport comparison](TRANSPORT-COMPARISON.md); adapter import-boundary and process-memory cost require a separate measurement.

A retry is safe only when non-dispatch is established for that operation; a generic disconnect or expired-session response does not resolve an earlier unknown write outcome.

## Security and process identity

Loopback is an address boundary, not caller authorization. The MCP transport text requires rejecting invalid present Origin headers, recommends local loopback binding and authentication; the official SDK guide additionally addresses Host validation for DNS rebinding. For a private automatic daemon, make the local adapter credential mandatory, separate it from Huly credentials, and validate it on every request. This is a proposed policy for the new managed mode, not a claim that every existing HTTP use must change. Native callers may omit Origin; an absent Origin does not substitute for authentication. [MCP transport security](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/draft/basic/transports/streamable-http.mdx), [SDK HTTP guidance](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/http.md).

An existing precedent is VS Code Remote-SSH: a per-user server uses a random local port plus a randomly generated connection key in user-protected storage. A random port by itself is not access control. Protect locator/configuration files against other OS users and verify daemon identity before transferring resolved Huly credentials. A bearer token authenticates the caller to the listener; it does not independently prove that an impostor listener knows the expected daemon secret. MCPorter's challenge handshake is a concrete mutual-authentication pattern to study, not an instruction to copy its full protocol. Same-user malware able to read the process's credential files is outside the isolation promised by ordinary per-user files. [VS Code multi-user guidance](https://code.visualstudio.com/docs/remote/troubleshooting#_improving-security-on-multi-user-servers), [MCPorter authentication implementation](https://github.com/openclaw/mcporter/tree/1e3fa8a893e3245a0843f714f81bfdf3b0ad5dbc/src/daemon).

Shared Huly resources must not imply shared mutable JSON-RPC routing state. The TypeScript SDK advisory GHSA-345p-7cg4-v4c7 documents cross-client leaks from reusing transport/server objects: independent clients can generate the same request ID and overwrite stream routing. It affects SDK1.x versions1.10.0–1.25.3, with guards added in1.26.0. Our server uses Effect's protocol implementation; this research does **not** establish that our server has that SDK vulnerability. The transferable requirement is isolation of request IDs, responses, progress, cancellation and client-directed messages while intentionally sharing only compatible backend resources. [Advisory and exact affected versions](https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-345p-7cg4-v4c7).

Credential rotation, profile logout, changed workspace and changed tool permissions must invalidate or separate the appropriate shared resources. A profile display name, workspace string, incoming MCP client name, or legacy session ID is not authorization. Do not publish raw credentials, credential-bearing URLs, command arguments or environment snapshots in locator files/status/logs; opaque owner identifiers need not disclose them. Huly self-hosted URLs may legitimately point at private addresses, so a blanket private-address ban would break the supported deployment. Trust the resolved configuration boundary rather than accepting arbitrary model-controlled pool destinations. [MCP local-server guidance](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/docs/2026-07-28/tutorials/security/local-server-security.mdx), [security best practices](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx).

## Concrete platform traps

- Windows file protection is not POSIX chmod: Node24.14.0 documents that only write permission can be manipulated and owner/group/other distinctions are not implemented. A token file created with mode0600 is not sufficient Windows ACL evidence. Use an OS-protected store or verified current-user ACL; test this on Windows. [Pinned filesystem API](https://nodejs.org/download/release/v24.14.0/docs/api/fs.html).
- Detached launch needs explicit ownership: `detached` and `unref()` alone do not detach inherited stdio. Prefer the installed Node executable plus our resolved entrypoint, without a shell or `.cmd` wrapper; sanitize inherited environment and account for Windows case-insensitive variable names. Windows termination semantics differ from POSIX signals, so use an authenticated drain operation for normal shutdown and independently test crash/forced termination. [Pinned child-process API](https://nodejs.org/download/release/v24.14.0/docs/api/child_process.html).
- Bind an explicit loopback literal. An omitted host can bind a wildcard; allocating port0 lets the listener choose a free port atomically instead of checking a port and later trying to claim it. Publish the actual endpoint only after application readiness. Our own comparison already demonstrated that an open TCP port was insufficient readiness admission; see its retained pilot boundary. [Pinned networking API](https://nodejs.org/download/release/v24.14.0/docs/api/net.html), [local comparison](TRANSPORT-COMPARISON.md).
- Stale-PID bugs are not hypothetical: QMD issue806 reported a recycled PID blocking startup and exposing an unrelated process to stop's SIGTERM. Fix commit3c861a1 adds process-command identity checks; current pinned code still relies on Linux `/proc` or POSIX `ps`, so it is not a Windows ownership recipe. We did not reproduce the historical issue. Command-name matching is also weaker than a generation-bound endpoint/process identity. [Issue806](https://github.com/tobi/qmd/issues/806), [fix](https://github.com/tobi/qmd/commit/3c861a1), [pinned current helper](https://github.com/tobi/qmd/blob/86d2365d17fc682e491c2c53d1e4a884aee8682a/src/cli/mcp-pid.ts).
- A lock library does not decide daemon ownership for us. `proper-lockfile` documents limits around manual lock removal and differing stale/update policies, and fatal exits can leave lock state. Reusing its pattern would still need a rule for paused processes, stale recovery and split ownership; no new dependency is selected here. [Library's stated limits](https://github.com/moxystudio/node-proper-lockfile#compromised).

Cross-platform HTTP does not by itself qualify every credential path. Our current native profile backend factory supports macOS Keychain and Linux Secret Service, not a Windows native backend; Windows callers currently need supported file storage or environment injection. Our native HTTP path avoids the need to multiplex all clients onto one upstream stdio stream. It still needs independent client/request routing and deliberate shared-resource ownership. Do not add a single shared SDK transport as a shortcut for sharing the Huly model.

## Research recommendation and evidence boundary

The narrow candidate is an own-package stdio adapter to the existing native loopback HTTP backend, with one resident backend per **compatible resolved configuration**, owned by one OS user. Keep direct HTTP and existing standalone stdio available. Do not introduce a generic multi-server gateway, third-party installed service, cross-user pool, or heap-reduction project in this task.

A process per compatible configuration is a simpler initial boundary than a universal daemon holding many mutable credential views. Different identities or policies may intentionally produce multiple resident backends; one daemon for the entire machine is not the success criterion. MCPorter's immutable views remain useful reference material if broader pooling becomes necessary later. This is a research recommendation, not an approved implementation or a claim that an automatic lifecycle is already built.

The proposed lifecycle needs explicit contracts for serialized launch, application readiness, authenticated attachment, immutable compatibility identity, active-request drain, generation changes, unknown outcomes and bounded recovery. If a write was dispatched before a disconnect, return an uncertain outcome; reconnecting must not silently replay it. No exactly-once guarantee follows: safe recovery requires operation-specific idempotency or reconciliation. Closing one stdio adapter cancels/releases its own requests and lease, not another adapter's work. Idle expiry must account for queued/active calls and lost adapters; a permanent counter without leases can leak forever after a crash. A fixed timeout must not kill legitimate long-running work.

Before adopting this design, demonstrate separate-parent simultaneous launches, an aborted launcher, stale locator/lock/PID/occupied port, same JSON-RPC IDs from different clients with deliberately different read payloads/results, one-client cancellation, daemon death during a write, idle expiry racing a new call, credentials rotation/logout, two package versions, lost stdout consumer/backpressure, and native Windows/macOS/Linux lifecycle behavior. These are proposed discriminating acceptance cases derived from the survey, not tests run in this research. Heap reduction is deferred as requested. The adapter's own import/memory cost and actual host lifecycle remain unmeasured. The prior performance matrix used identical read workloads across clients, so its parity success does not independently prove adversarial cross-client routing isolation.
